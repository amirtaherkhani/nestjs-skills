# Bounded collection selection

Run `npm run test:fixtures` from the repository root. The NestJS 11.2.7 HTTP example accepts a JSON selection with at most 32 string IDs, a limit from 1 to 32, and a 4 KiB parser limit. The catalog and allowed IDs are server-owned here. A real data provider must also bound its database result and enforce authorization; accepting `allowedIds` from the request would defeat that boundary.

`selectCards` builds a request-local `Map` from catalog ID to the **first** row, and a `Set` of allowed primitive string IDs. It walks the original requested ID array, uses `continue` for denied or absent records, `push` for the result, and `break` when the output limit is reached. The output is a fresh array of fresh `{ id, title }` objects. Repeated requested IDs remain repeated and ordered; a repeated catalog ID retains the first row, matching `rows.find(row => row.id === id)`. Inputs are read only and remain caller-owned. If the query must outlive the immediate call, copy its ID array at that ownership boundary.

## Choose a collection for the job

| Shape | Use it for | Cost or semantic trap |
| --- | --- | --- |
| Array | Ordered rows, repeated IDs, JSON lists | A repeated `find` scans rows for each ID; a single `find` or `some` can stop early and is often clearest for small one-off work. |
| `Set<string>` | Repeated membership tests on validated primitive IDs | Construction and memory have a cost; deduplicating the response would change the contract. Objects compare by identity, not fields. |
| `Map<string, Row>` | A temporary index for repeated joins or dynamic user keys | `new Map(rows.map(row => [row.id, row]))` keeps the **last** duplicate; this example deliberately keeps the first. A Map is not a JSON response shape. |
| `Record<'scanned' \| 'returned', number>` | A fixed, known key set such as local counters | It is a TypeScript type, not runtime validation. Avoid an ordinary object as a dynamic lookup for untrusted keys such as `__proto__`; use Map or a null-prototype object. |
| `readonly [id: string, rank: number]` | A fixed two-position pair where both positions have distinct meanings | A tuple still compiles to an array and does not validate JSON. Named objects are clearer when fields may grow or cross a public boundary. |

Repeated immutable accumulator spreads (`reduce((all, item) => [...all, item], [])`) copy the prior result on every item and can produce quadratic total copying. `push` into a **new local** accumulator performs the same ordered construction without changing caller-owned inputs. A `filter(...).map(...)` pipeline can be clearer for small data; it makes intermediate arrays and cannot stop after the requested number of matches. Use `find`, `some`, or an explicit loop when the stop condition is part of the contract.

The sample indexes the entire catalog before it reaches the output limit. That setup is worthwhile when many requested IDs reuse a sizable row set. For a short input, one scan or a database join may be cheaper and simpler. If building the catalog itself is expensive, bound or page it at the data source; an in-memory `Map` cannot fix overfetching. For object keys, decide whether identity or a normalized stable primitive key expresses the domain's equality rule. Set and Map use SameValueZero equality; this example validates strings, so reference identity is irrelevant.

## Boundaries and evidence

The controller treats `@Body()` as `unknown`, rejects unknown fields and invalid types, and narrows only after checks. The Express JSON parser rejects bodies above 4 KiB before parsing. The exported selector independently rejects limits outside 1–32, including fractional and non-finite numbers, and checks output count, while the server-owned catalog is deliberately fixed and small. These are separate byte, item-count, and output bounds; neither a TypeScript annotation nor a post-parse array length check caps JSON parsing work. For a real service, add ingress limits, query/data-source limits, concurrency controls and measurements appropriate to its traffic. The example's response projection omits `internalToken`; it never serializes catalog rows directly.

Tests cover ordering, both duplicate cases, first-match semantics, absent and denied IDs, `__proto__`, caller-owned arrays, early output limit, invalid and oversized HTTP input, and the public response. They establish behavior under the pinned dependencies; they do **not** establish faster production latency or memory use. Benchmark a representative distribution of row counts, duplicate rates, hit rates and output limits after warm-up, with p50/p95/p99 latency, allocation/GC and event-loop delay. Compare the same workload and environment before and after, including index construction. The fixed test is not a throughput benchmark.
